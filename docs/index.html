1. Overview

Arch is an open-source, locally-run coding agent. This policy explains what data Arch does and does not handle, how the software is designed with respect to your privacy, and what applies to you differently if you interact with the project's community infrastructure (such as its repository host, issue tracker, or any optional hosted services) rather than the software itself.

Because Arch is open-source and, in its default configuration, runs entirely on your own machine, this policy is shorter and more specific than a typical commercial SaaS privacy policy. There is no central server operated by the maintainers that receives your code, prompts, or usage data through the ordinary operation of the software.

  • Contributors who interact with the project's public repository, issue tracker, or discussion forums.
  • Anyone who uses optional, clearly-labeled hosted or cloud features, if and when the project offers them.

This policy does not cover the privacy practices of third-party large language model (LLM) providers, cloud services, package registries, or other external tools you choose to connect to Arch. 2. Core Privacy Principle: Local-First, No Telemetry by Default

Arch is designed to run fully on your local machine. In its default configuration:

  • No source code, prompts, file contents, or command output is transmitted to any server operated by the maintainers.
  • No usage analytics, crash reports, or telemetry are collected or transmitted automatically.
  • No account, sign-up, or network connection is required to install or run the software.
  • Indexing, retrieval (RAG-based context lookup), multi-file editing, and verification loops all execute locally, using local compute and local storage.

This means that, unless you explicitly enable an optional feature that requires network access (such as connecting to a third-party model API), Arch has no visibility into your code, your prompts, or how you use the tool.

2.1 What “local-first” means in practice

3. Data Processed Locally

Although Arch does not transmit data externally by default, it does read, generate, and temporarily store certain data locally in order to function. This section describes that processing for transparency, even though it never leaves your machine under default settings.

3.1 Codebase content

To provide multi-file editing and context-aware suggestions, Arch reads files within the project directory you point it to, and may build a local semantic index (via RAG-based indexing) to retrieve relevant context efficiently. This index is stored locally, typically alongside the project or in a local cache directory, and is used only to serve your own queries.

3.2 Prompts and conversation history

Your prompts, the agent's responses, and any intermediate reasoning or tool-call records are kept in local session state to support features like session portability (resuming a session later) and verification loops (checking prior steps before proceeding). You can typically clear this history by deleting the relevant local cache or session files — see your local configuration documentation for the exact path.

3.3 Verification and execution data

Where Arch runs code, tests, or commands as part of a verification loop, the output of those commands is processed locally to inform the agent's next steps. This output is not transmitted anywhere by the core software.

3.4 Local logs

6. Third-Party LLM Providers and Integrations

Arch is model-agnostic and can be configured to work with local models or external, third-party model APIs, depending on how you set it up.

6.1 Local models

If you configure Arch to use a model that runs entirely on your machine (e.g. via a local inference server), no prompt or code data leaves your device as a result of model inference.

6.2 External model APIs

If you configure Arch to call an external, third-party LLM API, the prompts and relevant code context you send will be transmitted to that third party according to your configuration. In that case:

  • The third-party provider's own privacy policy and data retention practices govern that data, not this document.
  • Arch transmits only what is needed to serve your request (e.g. the active prompt and relevant context) — it does not upload your entire codebase or session history unless your configuration or the model's context window causes it to be included.
  • You are responsible for reviewing the terms of any third-party provider you choose to connect, especially before sending proprietary, confidential, or regulated code or data through it.

We recommend consulting the documentation for any model provider you configure (for example, its data retention window, whether it trains on submitted data, and regional data handling) before use.

6.3 Other integrations

Arch may support optional integrations with other developer tools (e.g. version control hosts, package registries, or MCP-compatible servers). Each integration only activates data flow to that specific third party if and when you explicitly configure it. Review the third party's privacy policy before enabling any such integration.

7. Data Security

Because Arch operates primarily on your local machine, the security of your data is largely governed by the security of your own device and any third-party services you choose to connect. That said, the project follows these practices:

  • Local data (session history, indexes, config) is stored using your operating system's standard file permissions; the software does not apply additional encryption by default unless noted in the documentation.
  • The project does not operate a central database of user data, which eliminates an entire category of breach risk associated with hosted services.
  • Dependencies are reviewed and updated as part of ongoing maintenance; users are encouraged to keep their installation up to date.
  • If you connect third-party APIs, credentials (e.g. API keys) are stored locally per your configuration — treat them with the same care as any other secret, and avoid committing them to version control.

Maintainer note: If you add a hosted component later (a backend service, telemetry endpoint, or account system), add specifics here: encryption in transit/at rest, access controls, breach notification process, and retention limits.
